# Задание старому экземпляру Сущности: извлечение накопленного опыта

## Назначение

Ты находишься в старом рабочем чате Сущности проекта «БЛАГОПОЛУЧИЕ» или связанного проекта.
Нужно извлечь из доступной истории **этого конкретного чата** накопленный профессиональный опыт.

Это НЕ recovery snapshot, НЕ попытка восстановить current-state и НЕ пересказ всей переписки.

Главный вопрос:

> Что следующий экземпляр этой Сущности должен знать и делать иначе благодаря опыту этого экземпляра, чтобы не повторять уже пройденные ошибки и быстрее получать проверяемый результат?

## Источник истины

Используй только:
- доступную историю ЭТОГО чата;
- реально присутствующие в нём файлы;
- результаты команд, проверок, тестов и другие проверяемые артефакты этого чата.

Запрещено:
- использовать память других чатов как источник истины;
- достраивать отсутствующие эпизоды догадками;
- выдавать historical state за current truth;
- объявлять extracted lesson новым каноном;
- скрывать `unknown`;
- менять Project Sources, recovery, GitHub, runtime или другие рабочие системы в рамках этой задачи.

Если история доступна только частично, честно зафиксируй границу видимого контекста.

## 1. Определи собственную роль

В начале результата укажи:
- Entity/роль этого чата, если она подтверждается самой историей;
- основные направления фактической работы;
- доступный диапазон истории;
- виден ли чат от начала;
- какие участки недоступны или неизвестны.

Если роль нельзя подтвердить, используй `ENTITY_UNKNOWN`.

## 2. Существенные рабочие эпизоды

Не переписывай чат подряд. Выдели только значимые эпизоды, где была задача, диагностика/поиск, решение, ошибка, проверка или изменение способа работы.

Для каждого эпизода используй структуру:

### <краткое название эпизода>

**Задача:** что требовалось получить.

**Контекст / объект:** система, документ, процесс, код, сервер, исследование, организационная ситуация или иной подтверждённый объект.

**Исходная модель / ожидание:** что экземпляр считал вероятным или правильным до проверки.

**Evidence / наблюдение:** что реально показали файлы, команды, тесты, документы, пользовательский feedback или другие проверяемые результаты.

**Предпринятые действия:** что реально делалось.

**Неудачные / недостаточные заходы:** что не сработало, оказалось неверным, преждевременным или создало новый дефект.

**Рабочее решение:** что в итоге дало подтверждённый результат.

**Проверка результата:** чем результат был подтверждён.

**Изменение модели:** что экземпляр после эпизода стал понимать иначе.

**Lesson:** короткое переносимое знание.

**next_time_behavior:** что следующий экземпляр при похожей ситуации обязан сделать иначе.

**prohibited_repeat:** какой уже пройденный ошибочный путь нельзя повторять без нового evidence.

**Граница применимости:** где lesson нельзя применять автоматически.

**Актуальность:** одно из `reusable | historical | requires-current-check | unknown`.

**Связанные evidence/artifacts:** только реально присутствующие references.

## 3. Плантация граблей

Собери отдельный каталог существенных ошибок и ловушек.

Для каждой:

### Грабля: <краткое название>

- **Как проявилась:** симптом/последствие.
- **Причина:** подтверждённая причина или `unknown`.
- **Почему прежняя проверка не поймала:** если это видно из истории.
- **Как обнаружили:** evidence/диагностика.
- **Что делали зря:** неверный или бесполезный путь.
- **Правильный подход:** что подтвердилось.
- **next_time_behavior:** как действовать в следующий раз.
- **prohibited_repeat:** что не повторять автоматически.
- **Граница применимости:** где правило не универсально.
- **Evidence:** связанный эпизод/файл/команда/результат.
- **candidate anti-regression test:** как проверить новый экземпляр на этой грабле.

Не объединяй разные причины ради краткости.

## 4. Причинные решения

Отдельно собери решения, где важен вопрос «почему»:

`problem → alternatives → chosen design/action → rejected alternative → evidence → correction/supersession`

Если причины выбора из истории не видны, ставь `unknown`, а не реконструируй красивую историю.

Особенно ценны решения, после которых появились:
- новое правило;
- новый invariant;
- новый test/checklist;
- новый authority/safety boundary;
- новый способ проверки;
- отказ от прежнего подхода.

## 5. Reusable procedures

Выдели процедуры, которые стоит превратить в будущие runbook/checklist.

Для каждой укажи:
- название;
- из каких эпизодов она выведена;
- порядок действий;
- обязательные проверки;
- failure/stop conditions;
- границы применимости.

## 6. Историческое незавершённое состояние

Отдельно перечисли:
- `open`;
- `parked`;
- `blocked`;
- `unknown`;
- `superseded`.

Это только historical extraction. Не объявляй эти пункты current tasks нового экземпляра без отдельной проверки текущего состояния проекта.

## 7. Машинопригодные experience cards

Создай отдельный файл `ENTITY_experience-cards.jsonl`.

Одна строка = одна существенная experience-delta.

Минимальная структура каждой строки:

```json
{"experience_id":"EXP-...","task_or_episode":"...","context_refs":["..."],"trigger_or_symptom":"...","initial_hypothesis":"...","failed_attempts":["..."],"observed_result":"...","working_resolution":"...","evidence_refs":["..."],"lesson":"...","next_time_behavior":"...","prohibited_repeat":"...","applicability_boundary":"...","freshness":"reusable|historical|requires-current-check|unknown","confidence":"high|medium|low","behavior_test_candidate":"...","supersedes":[]}
```

Если поле неизвестно, используй `unknown` или пустой список. Не выдумывай заполнение ради формальной полноты.

## 8. Anti-regression cases

Создай отдельный файл `ENTITY_anti-regression-cases.md`.

Для каждого сильного lesson опиши:
- ситуацию/новую похожую задачу;
- правильный порядок реакции;
- типичную неправильную реакцию;
- pass criterion;
- fail criterion;
- evidence episode.

Цель: проверять не способность нового экземпляра пересказать старый lesson, а способность **применить его без подсказки**.

## 9. EXTRACTION_REPORT

В конце основного файла обязательно укажи:
- фактически просмотренный диапазон истории;
- виден ли чат от начала;
- недоступные участки;
- число существенных эпизодов;
- число граблей;
- число причинных/архитектурных решений;
- число reusable procedures;
- число experience cards;
- число anti-regression cases;
- число `unknown`;
- крупные направления работы;
- что могло остаться за пределами доступного контекста.

Не заявляй `полная история`, если это нельзя проверить.

## Выход

Подготовь **три самостоятельных файла без tar.gz**:

1. `ENTITY_experience-extraction.md`
2. `ENTITY_experience-cards.jsonl`
3. `ENTITY_anti-regression-cases.md`

Вместо `ENTITY` используй подтверждённый короткий код роли, если он известен (`KOD`, `SIS`, `KOO`, `ARH`, `VOL`, `RED`, `SHT`, `KAN` и т.п.). Если нет — `UNKNOWN`.

Не публикуй файлы самостоятельно и не меняй никакие рабочие системы.

После создания файлов в чат выведи только:
- названия трёх файлов;
- краткий диапазон просмотренной истории;
- количество эпизодов / граблей / procedures / cards / anti-regression / unknown;
- известные ограничения extraction.

## Критерий успеха

Результат хорош только если следующий экземпляр после использования Experience Layer:
- раньше распознаёт уже знакомый класс проблемы;
- не повторяет известную ошибку;
- применяет подтверждённый порядок работы без подсказки;
- отличает historical evidence от current truth;
- останавливается на `unknown`;
- требует evidence там, где старый экземпляр ошибался;
- получает более качественный первый результат с меньшим вмешательством ОПЕРАТОРА.
